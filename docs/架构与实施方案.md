## 2. 技术栈（本次落地）

- 后端：PHP 8.4 + Laravel 13
- 数据库：PostgreSQL（本地开发用 17 实例的 16 版本服务，生产与 Alibaba Cloud RDS 一致）
- 文件存储：腾讯云 COS（`overtrue/flysystem-cos` + `qcloud/cos-sdk-v5`），本地开发默认走 `local` 磁盘，`.env` 切换 `FILESYSTEM_DISK=cos` 即可切到云端
- 前端：Blade + Alpine.js，直接复用 UI 原型（`图纸变更管理系统-UI设计.html`）的配色 / 字体 / 交互，替换为真实接口驱动

## 3. 权限模型

四级角色：`construction`（施工方）/ `designer`（设计师）/ `admin`（管理员）/ `super_admin`（超级管理员），存于 `users.role`。

**管理层（admin + super_admin）= 设计师全部内容管理权限 + 团队/专业管理 + 后台入口**（对应 `User::canManageContent()` / `isAdminTier()`，内容类操作统一按这些方法判断，而不是单独判断 `isDesigner()`，否则会出现管理员反而不能管理细分类的问题——这个坑在本地验证阶段被 Feature 测试和手动过一遍角色切换时发现并修正过）。

**admin 和 super_admin 的唯一区别**：只有 `super_admin` 能创建 / 编辑 `admin` 或 `super_admin` 级别的账号（`User::canAssignRole()`），普通管理员只能管理 `designer` / `construction` 账号，防止随意提权。

- **项目可见性**：非管理层账号仅能访问 `user_project` 中绑定的项目；管理层绕过此限制。
- **团队可见性**：非管理层账号仅能访问 `user_team` 中绑定的团队（比如只负责机电、看不到土建/精装）；管理层绕过此限制。项目和团队两个维度是"与"关系，两个都要匹配才放行。
- **团队 / 专业结构**：全公司统一标准分类，仅管理层可增删改，改动对所有项目生效。
- **细分类**：项目级数据，`designer` / 管理层在可见项目 **且** 可见团队内自行维护；`construction` 只读。
- **版本 / 语言文件**：`designer` / 管理层可上传新版本、补充或替换语言文件、删除版本（中文版本不可移除）；`construction` 只能查看、预览、下载。
- **删除确认**：细分类 / 团队 / 专业删除均需二次输入密码，后端用 `Hash::check()` 校验当前登录账号的真实密码，不是前端固定密码。
- **个人设置**：任何账号都能在 `/profile` 自助修改姓名和密码（改密码需先验证当前密码），登录标识 `login_id` 不可自助修改。

对应实现：`app/Policies/*Policy.php`（`SubcategoryPolicy` / `VersionPolicy` / `VersionFilePolicy`，均同时校验 `hasProjectAccess()` 和 `hasTeamAccess()`）+ `manage-taxonomy` / `manage-users` Gate + `EnsureUserHasRole` / `EnsureProjectAccess` 中间件。

**授权时的一个真实踩坑**：`$this->authorize('create', [$version])` 这种写法，Laravel 会按数组里第一个模型的类名去找 Policy，误把 `VersionFile` 的创建判断路由到了 `VersionPolicy`。必须显式写成 `$this->authorize('create', [VersionFile::class, $version])` 才会正确解析到 `VersionFilePolicy`。这个 bug 是 Feature 测试跑出来的，见 `tests/Feature/VersionFileLanguageTest.php`。

## 3.1 站内通知

新版本发布后，系统会给"同时拥有该项目权限和该团队权限"的 `designer` / `construction` 账号（不含上传者本人）各发一条站内通知（`App\Notifications\NewVersionPublished`，走 Laravel 标准 `database` 通知渠道）。管理层已经能看到全部内容，不需要额外通知。

顶部导航栏有通知铃铛显示未读数，`/notifications` 列表页可以查看、点击跳转到对应细分类、标记已读 / 全部已读。

**后续可扩展方向**（本期未做）：
- 浏览器推送：页面开着时用 Notification API 弹提示，工作量小；要做到关闭页面也能收到，需要 Web Push（VAPID 密钥 + Service Worker + HTTPS），工作量更大。
- 企业微信：群机器人 webhook 简单；要精准发给某个人，需要企业微信自建应用（CorpID/Secret/AgentId）并做账号映射。
- 微信公众号：模板消息需要认证服务号 + 用户关注 + openid 绑定流程，基础设施要求最高，目前完全没有前提条件。

## 3.2 图纸预览（已从 DWG→DXF 改为 PDF）

**历史方案（已停用）**：DWG 上传后，后端自动调用免费的 ODA File Converter 转出 DXF，浏览器端用开源的 dxf-viewer（WebGL）交互式渲染。这套方案在实际使用中有个绕不开的问题——转换本身可能要等到 1 分钟，还必须有 `queue:work` 常驻进程处理，运维成本偏高。详见 [DWG看图接入说明.md](DWG看图接入说明.md)（现在只作为历史记录保留）。

**当前方案**：图纸预览直接读取 `kind=pdf` 的 `VersionDrawing` 记录，用 `<iframe>` 嵌入浏览器自带的 PDF 阅读器（`VersionDrawingController::preview()` 签发一个 inline 的临时访问 URL），翻页、缩放全部是浏览器原生能力，不需要任何服务器端转换、不需要队列 worker、不需要引入前端库。有多份 PDF 时用 chip 切换。没有 PDF 就显示"暂无图纸预览"，DWG 原图本身始终可以正常下载，只是不再有交互式预览。

`App\Services\DwgConverter`、`App\Jobs\ConvertVersionDrawingDxf`、`version_drawings.dxf_path`/`dxf_status` 这些代码和字段都还留在仓库里（没有删除，方便以后想恢复），只是不再被上传流程调用。

## 3.3 一次变更的多文件模型

一次变更（`Version`）不再假设每个语言只有一份 DWG：实际经常是每层一张图，PDF 也是同理，可能有多份。数据结构上拆成两块：

- **DWG 原图 / PDF 图纸**（`VersionDrawing`，见[数据库设计.md](数据库设计.md)）：同一语言下可以有任意多份，随时可以单独追加、单独删除，互不影响；每份各自记录上传时间（即"补充日期"）。唯一的强制项是中文至少要保留 1 份 DWG——`App\Http\Controllers\VersionDrawingController::destroy` 会检查这条规则，删光最后一份会被拒绝。
- **变更说明文件**（`VersionFile`）：每语言最多一份，格式不限于 Word/Excel，也支持 txt、甚至 dwg（比如说明本身就是一份带批注的 DWG），现在所有语言都是可选，不再强制要求。

按语言打包下载：`GET /versions/{version}/languages/{language}/zip`（`VersionDrawingController::downloadZip`），把该语言下所有 DWG + PDF + 说明文件用 `ZipArchive` 现打包现下载，用完即删临时文件。

## 3.4 界面多语言（法语）

用 Laravel 标准的 JSON 翻译文件机制，`resources/lang/fr.json`：一份"中文原文 → 法语译文"的对照表，中文本身不需要单独的翻译文件（找不到译文时 `__()` 直接返回原文，天然就是中文）。

- `App\Http\Middleware\SetLocale`（挂在 `web` 中间件组，全站生效）从 `session('locale')` 读取语言，默认 `zh_CN`；`GET /language/{locale}` 切换并写回 session，纯会话级别，不落数据库，退出登录会话失效后自动回到中文。切换入口：登录页和主布局顶部导航栏都有"中文 / Français"按钮。
- 覆盖范围是**主要内容页**（登录、总览、项目/细分类/变更详情、语言文件管理、图纸预览、个人设置、站内通知列表）以及这些页面对应控制器生成的提示文案（toast、校验错误）。**后台管理（`/admin/*`）不翻译**，仍是纯中文，因为那是内部管理员专用界面。
- **只翻译静态界面文案，不翻译数据**：团队/专业/细分类名称、变更说明文字、上传人姓名、站内通知里已经生成好的具体内容，这些都是用户自己录入或系统生成的实际数据，不是界面文案，法语模式下依然按原样显示（不可能有通用词典能"翻译"一段用户自己写的中文变更说明）。
- 译文如果哪里翻得不准确/不地道，直接改 `resources/lang/fr.json` 对应的 value 即可，key（中文原文）不要动，否则会对不上。

## 8. 上线前安全加固（本次上线 review 新增）

对照生产环境做了一轮安全审查，补上了这几处此前没做的加固，都已落地：

- **登录限流**：`POST /login` 加了 `throttle:6,1`（同一来源 1 分钟最多 6 次），防暴力破解密码。
- **登录验证码**：用 `mews/captcha`（本地 GD 生成图片，不依赖谷歌 reCAPTCHA 这类外部服务），配色跟着"材料样板"主题走（`config/captcha.php` 的 `honsen` 预设）。测试环境用 `.env`/`phpunit.xml` 里的 `CAPTCHA_DISABLE=true` 跳过，不需要在自动化测试里"解"验证码图片。
- **反向代理信任**：`bootstrap/app.php` 配置了 `trustProxies(at: '*')`，因为部署时 Nginx（宝塔）在同一台机器上终止 SSL 再转发给 PHP-FPM，不信任代理的话 Laravel 会把请求误判成 HTTP、拿到的客户端 IP 也是内部转发地址而不是真实来源。
- **生产种子数据风险**：见上一节，新增 `app:create-admin` 命令替代演示 seeder。
- **上传大小与 PHP 层配置的一致性**：`config/uploads.php` 加了注释提醒 `upload_max_filesize` / `post_max_size` 要同步调整，具体数值见 [README.md](../README.md) 部署步骤第 2 步。
- **Session Cookie**：`.env.example` 补充了 `SESSION_SECURE_COOKIE`，生产 HTTPS 环境必须设为 `true`。

详细部署步骤（含以上各项在 `.env` 里的具体值）见项目根目录 [README.md](../README.md)。

生产环境上线前需要把这些演示账号删掉或改密码，正式账号通过后台"账号管理"页面创建。
